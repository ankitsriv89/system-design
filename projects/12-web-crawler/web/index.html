How a Web Crawler Works

The Problem

A web crawler must visit billions of pages without hammering any single server, without revisiting the same page twice, and without storing infinite duplicate content. Three hard problems: frontier scheduling, politeness, and deduplication.

Frontier Queue

The frontier is a priority queue of unseen URLs. This implementation uses a PostgreSQL table with SELECT FOR UPDATE SKIP LOCKED so multiple workers can pull work concurrently without contention. URLs are scored by priority and next_fetch_at.

Politeness & robots.txt

Before fetching any URL the worker checks a per-host robots.txt rule cached in Redis (24h TTL). If the path is disallowed it's skipped. Between requests to the same host the worker sleeps for crawl-delay (or 1s default). This prevents overloading any single origin.

Deduplication

Each URL is hashed (SHA-256) and checked against a Redis SET before any work is done. After a successful fetch the hash is added. Identical content from different URLs is detected via a content hash stored in PostgreSQL.

Scale Path

MVP: 3 goroutine workers, single Postgres + Redis. Production: partition the frontier by host hash across worker shards; replace the Redis SET with a distributed Bloom filter; push discovered URLs through a message bus (Kafka) so fetching and parsing are independently scaled.

Algorithm Step-Through

  1. Worker claims up to 5 URLs with SELECT … FOR UPDATE SKIP LOCKED
  2. Check Redis SET for URL hash → skip if seen
  3. Fetch robots.txt for host (cache-first, 24h TTL)
  4. Check path against Disallow rules → skip if disallowed
  5. Sleep crawl-delay (default 1s) for host politeness
  6. HTTP GET with 15s timeout, 2MB body cap, 5 redirect limit
  7. Compute SHA-256 of body → detect duplicate content
  8. Extract <a href> links, normalise, enqueue unseen ones
  9. Mark URL done in frontier; add hash to Redis seen-set
