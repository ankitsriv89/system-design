How It Works

WebSocket Hub

Each user opens a persistent STOMP/WebSocket connection. The server's Hub maps userId → session, routing messages to the correct recipient without broadcast.

Message Ordering

A monotonic seq counter per conversation guarantees total order. Assigned under a transaction lock — no two messages share a seq.

Kafka Fanout

After persistence, the message is published to Kafka partitioned by recipientId. The consumer delivers it over WebSocket if the recipient is online, or leaves it in Postgres for offline pull.

Offline Delivery

When a user reconnects, the client fetches GET /api/v1/conversations/{id}/messages?before=<lastSeen> to catch up on missed messages from Postgres.

Presence (Redis TTL)

Each WebSocket heartbeat refreshes a Redis key presence:{userId} with a 30 s TTL. A user is "online" as long as that key exists. On disconnect the key is deleted immediately.

Read Receipts

SENT → DELIVERED (WebSocket ACK from Kafka consumer) → READ (client sends explicit receipt frame). Status transitions are append-only — never downgraded.
