How it works — LSM-tree

An LSM-tree (Log-Structured Merge-tree) optimises for write throughput by never doing random I/O. Every write is sequential.

1. Write path

A write is appended to the WAL (Write-Ahead Log) and fsynced. The WAL is the durability guarantee — if the process crashes the write survives. The key is then inserted into the in-memory memtable (a sorted hashmap). The call returns immediately after the fsync.

2. Flush to SSTable

When the memtable exceeds 4 MiB it is frozen and written sequentially to a new SSTable (Sorted String Table) on disk at Level 0. SSTables are immutable — they are never modified in place.

3. Compaction

Over time many L0 SSTables accumulate. A background job merges them into one larger L1 file, resolving duplicates (newest wins) and dropping tombstones. This reduces read amplification and reclaims space.

4. Read path

A read checks the memtable first, then scans SSTables newest-first until the key is found or all files are exhausted. A tombstone record signals deletion.

Why LSM over B-tree?

B-trees do random I/O on every write (page split, COW). LSM turns all writes into sequential appends, giving 10–100× better write throughput on spinning disks and significant gains on SSDs. The trade-off is higher read amplification and the compaction overhead.
