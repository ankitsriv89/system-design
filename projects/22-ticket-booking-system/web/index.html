Ticket Booking System

Inventory locking · Hold TTL · Payment saga · Oversell prevention

How It Works

Three-Phase Booking

1
Browse Seat Map

Cached in Redis (30s TTL). Stale on any seat state change.

↓
2
Place Hold

Optimistic lock on seat row (@Version). Hold written to PG + Redis. TTL: 5 min.

↓
3
Checkout

Idempotency key prevents double-charge. Payment mock: amount > 0 succeeds. Seat → BOOKED.

Oversell Prevention

Two guards in series: (a) Redis key seat_hold:<id> is checked first — fast rejection. (b) PostgreSQL optimistic locking (@Version) catches any remaining race. Only one transaction can flip AVAILABLE → HELD.

Hold Expiry

A Spring @Scheduled worker sweeps expired holds every 10 s. It sets hold.status = EXPIRED, returns the seat to AVAILABLE, evicts the seat-map cache, and publishes hold.expired to Kafka.

Key Design Decisions

  • Strong Seat state is always consistent — PG is source of truth
  • Eventual Seat map cache — 30 s max stale window
  • Idempotent Checkout accepts idempotencyKey — safe to retry
  • Scale Flash-sale: partition by event_id; Redis atomic SET NX before DB
